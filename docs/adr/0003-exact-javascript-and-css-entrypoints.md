# 0003 — Exact JavaScript and CSS entrypoints

**Status:** accepted

## Decision

One subpath per family, no layer barrels, and CSS split per family beside it. `core.css`
carries tokens, themes, and the cascade layer order; every family stylesheet imports it,
making the family stylesheet a self-contained consumer entrypoint.

## Why

A barrel makes every consumer's bundle the union of every family. Worse, it makes an optional
peer reachable from an import that never asked for it: `themelia-ui/base` would put
Recharts in the resolution graph of an application that only wanted a button.

Splitting CSS the same way follows from the same argument, and was harder than it looked. The
first attempt concatenated each family's transitive closure, which produced a 4.1MB
`style.css` and a 7.4MB `dist` — the same shared chunks written once per family that reached
them. The shipped version emits each chunk's CSS once and makes the family sheets `@import`
indexes over them.

The layer order lives in `core.css` rather than being copied into each sheet. Family
stylesheet indexes import `core.css` first, preserving that order without asking every
consumer to remember a second import.

## Consequences

- 187 export entries in `package.json`, generated by `gen-exports.mjs`.
- A bundler resolving the ESM entry gets the shared core stylesheet automatically, while a
  consumer imports the exact family stylesheet for its visual rules. Node cannot `import` a
  `.css` file, so the CJS entry must carry no CSS import — `verify package` executes the CJS
  build in Node and fails if it does.
- `style.css` still exists as the deduplicated union, for consumers who would rather not
  track sheets.
- Adding a family means regenerating exports, not hand-editing `package.json`.

## What would justify revisiting

- A bundler ecosystem where per-family CSS imports stop being resolvable.
- Measured evidence that the many-entry build costs more than the bytes it saves consumers.
